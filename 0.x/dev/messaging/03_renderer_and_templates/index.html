    Renderer and Templates

    Where rendering happens

    There are exactly two valid places to render a transactional email body:

    1. Worker side (Mode 1, TemplateNotificationDTO): the worker has a templates directory + Jinja2; the host pushes only template path + context key. This is the default mode, used today for booking and campaign emails.
    2. Host side (Mode 2, RenderedNotificationDTO): the host renders HTML in its own template engine (Django, Jinja2-on-FastAPI, etc.); the worker passes the bytes through. Used for admin alerts and the compose-new flow once it is fixed.

    A given event MUST pick exactly one mode. Mixing the two for the same template key is a bug — the resulting two paths drift in subtle ways (date formatting, i18n, base layout).

    Rendering decision tree

    Does the host have a template engine that produces the layout you want?
├─ Yes → Mode 2 (RenderedNotificationDTO)
│        Use case: admin alerts, compose-new outbound, anything that
│        needs i18n or request context.
│
└─ No → Mode 1 (TemplateNotificationDTO)
         Use case: booking lifecycle, campaign sends, anything where
         the worker template directory is the single source of truth.

Does the content depend on data that changes between enqueue and send?
├─ Yes → Mode 1 (re-fetch from Redis at render time)
│
└─ No → Mode 2 (snapshot at enqueue time)

    In practice: * Booking confirmations are Mode 1 (reschedule may change time between enqueue and send). * Campaigns are Mode 1 (recipient personalization variables — name, locale — must merge with the template at the worker). * Admin alerts on a new contact form are Mode 2 (small, no late-binding, generated by Django). * Compose-new outbound (the broken flow) becomes Mode 2 (host renders the body, worker just delivers; see lily migration doc 01).

    TemplateRenderer (current, unchanged)

    renderer = TemplateRenderer(templates_dir="/path/to/workers/templates")
html = renderer.render("booking/bk_confirmation.html", context={...})
    • Wraps jinja2.Environment with FileSystemLoader and HTML autoescape.
    • Raises RuntimeError if jinja2 is not installed — Mode 2 hosts do not need to install it.
    • Raises FileNotFoundError if the templates directory does not exist (fail-fast at worker boot is intentional).

    Template-key conventions

    The lily worker uses prefix-based directory routing in NotificationService.resolve_template_path():

    Prefix Directory Examples
    bk_* booking/ bk_confirmation, bk_cancellation, bk_reminder, bk_no_show, bk_group_booking
    ct_* contacts/ ct_receipt, ct_reply
    mk_* marketing/ mk_basic (campaigns)
    acc_* account/ acc_verification, acc_password_reset, acc_already_exists

    The platform documents this convention but does not enforce it. Two options for projects with a different layout:

    1. Pass a fully qualified path (e.g. customer/welcome.html) — the prefix logic is bypassed.
    2. Override the resolver in a project-specific subclass of NotificationService.

    The messaging package exposes a small helper so the resolver does not get reinvented per project:

    def resolve_template_path(template_name: str, prefix_map: dict[str, str] | None = None) -> str:
    """Map 'bk_confirmation' -> 'booking/bk_confirmation.html' using prefix_map."""

    prefix_map defaults to the lily layout; projects pass their own when needed.

    Context contract

    The renderer receives whatever dict the host stored under context_key. The platform makes no guarantees about which keys exist — that is a project + template contract.

    However, for sustainable templates we recommend a base set of keys that every email layout uses, populated by the host:

    {
    # Branding (from EmailSettings)
    "site_url": "https://example.com",
    "logo_url": "https://example.com/static/logo.png",
    "company_name": "Lily Beauty Salon",

    # Recipient
    "first_name": "Anna",
    "last_name": "Müller",
    "locale": "de",

    # Domain payload (varies)
    "appointment": {...},
    "unsubscribe_url": "...",
}

    The lily worker enriches the context further (greeting based on visit count, parsed datetime, calendar deep-link) inside NotificationService.enrich_email_context. This is project logic and stays project-side; the platform does not touch it.

    Mode 2 — what the host renders

    When the host renders, it produces a string and passes it via RenderedNotificationDTO.html_content. Two rules:

    1. Inline all CSS. The platform does not transform HTML; whatever the host renders is what the recipient sees. Use a CSS inliner in the host pipeline (e.g. premailer).
    2. Provide a text fallback. If text_content is absent, the SMTP channel emits the literal string "Please enable HTML to view this email.". That is a poor user experience; hosts should always provide a plain-text representation.

    Anti-patterns

    • Rendering HTML in the host AND passing template_name to the worker. The worker rejects payloads with both fields set. Pick one mode per event.
    • Mutating the context dict after enqueue in Mode 2. Mode 2 is a snapshot. If you need late-binding, switch to Mode 1.
    • Reading from Django ORM inside a Jinja2 template that the worker renders. Workers MUST NOT import Django. Pre-fetch all data on the host side and ship it in the context.
    • Using project-specific paths ('features/booking/templates/...') in the template name. The worker has its own TEMPLATES_DIR and does not know about Django app paths.
